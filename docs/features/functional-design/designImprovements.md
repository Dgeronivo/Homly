# Пропозиції покращення функціонального дизайну

*Дата створення: 2026-07-19*

Базується на [currentDesign.md](currentDesign.md). Для кожної фічі/екрана — варіанти покращень з приблизною складністю реалізації (не зачіпаючи кольори/відступи/дизайн-систему). Складність оцінена відносно поточного розміру фіч (MVVM, Room, use case на кожну дію):

- **Низька** — 1 екран, без нових сутностей/полів у БД, здебільшого UI + невеликий use case.
- **Середня** — потрібна нова колонка/сутність або новий стан у ViewModel, можливо нова таблиця.
- **Висока** — новий флоу, нова доменна модель, міграція між екранами або кілька фіч одночасно.

---

## 1. Головна сторінка (Home) — найсиріша, тому найбільше уваги

Зараз: привітання + 3 кнопки-посилання + Log out, все по центру екрана. Немає жодної інформації про стан даних — користувач не знає, чи є в нього незакриті завдання, події сьогодні, чи список покупок взагалі не порожній, поки не відкриє фічу.

### Варіант A — Картки фіч зі зведенням (рекомендовано)
Замінити кнопки-рядки на 3 картки (Calendar / Shopping / Todo), кожна з коротким summary:
- Calendar: "Today: 2 events" або "No events today".
- Shopping: "5 items left to buy".
- Todo: "3 tasks pending".

Дає користувачу причину відкрити фічу, а не просто список назв. Не змінює бізнес-логіку фіч — лише читання вже наявних даних (count) на Home.
**Складність: середня** (потрібні 3 легкі запити типу "count active items today/pending" у кожному repository + невеликий HomeViewModel рефактор для paralel collect).

### Варіант B — "Сьогодні" секція над кнопками
Над трьома кнопками — блок "Today", що показує список подій календаря на поточну дату (як міні-агенда), без чисел по інших фічах.
**Складність: середня** (переюзати GetEventsUseCase з фільтром на today; UI — простий LazyColumn/список із 1-3 рядків).

### Варіант C — Мінімальний: перейменувати й додати іконки
Не чіпаючи дані, просто замінити текстові Button на картки з іконками (📅 🛒 ✅) без summary-тексту. Суто візуальне окремо від чисел.
**Складність: низька.** Але ефект помітно менший за A/B — сама структура ("список посилань") залишається тою ж.

### Варіант D — Підтвердження виходу
Зараз Log out спрацьовує миттєво без діалогу підтвердження — легко натиснути випадково (кнопка внизу списку інших дій). Додати AlertDialog "Log out? / Cancel".
**Складність: низька.**

**Рекомендація:** A (або A+D разом) — найбільший приріст функціональності Home за помірні зусилля, не чіпає бізнес-логіку фіч, лише додає читання агрегованих даних.

## 2. Аутентифікація (Login / Register)

Дизайн функціонально достатній для одноосібного/сімейного планувальника без відновлення паролю через бекенд (це офлайн Room-застосунок). Основні прогалини:

### Варіант A — Показати правила логіну/паролю до вводу помилки чіткіше
Зараз hint замінюється помилкою лише після вводу невалідних символів — ок, але немає live-індикатора (галочка/хрестик по мірі набору). Можна лишити як є.
**Оцінка: покращення не є необхідним** — поточний supporting-text патерн (правило → помилка) простий і зрозумілий, змінювати ризиковано за мінімальний виграш.

### Варіант B — "Показати пароль" (іконка ока)
Зараз пароль завжди прихований (PasswordVisualTransformation без перемикача). Додати IconButton toggle видимості.
**Складність: низька** (лише UI-стан у Composable, без змін ViewModel/domain).

### Варіант C — Запам'ятати останній логін / залишатись увійденим довше
Сесія й так зберігається (DataStoreSessionRepository) — тобто "email pre-fill" не на часі, autologin вже є. Пропускаємо.

**Рекомендація:** тільки B, як дрібне покращення зручності; решта екрана вважаю достатньо функціональною.

## 3. Календар

Це найбільш пропрацьована фіча (місяць-сітка, day picker, лічильник подій, snackbar на ліміт). Основні прогалини — не в поточних екранах, а у відсутності швидшого огляду:

### Варіант A — Показ часу/назви першої події прямо в клітинці дня
Зараз крапка під числом лише сигналізує "є подія(ї)", без деталей. Можна показати кількість (маленька цифра) замість крапки, якщо подій >1.
**Складність: низька** (чиста UI-зміна: замінити Box-крапку на Badge з count, дані вже є в daysWithEvents — треба тільки перейти від Set<LocalDate> до Map<LocalDate, Int>).

### Варіант B — Список подій "на сьогодні" завжди видимий (не тільки обраний день)
Наприклад, невеликий чіп "Today" для швидкого повернення до поточної дати, коли переглядаєш інший місяць.
**Складність: низька** (кнопка + onDateSelected(LocalDate.now()) + onMonthChanged(YearMonth.now())).

### Варіант C — Розрізнення категорій подій (кольорові мітки/типи)
Наприклад "сімейна подія" / "особиста" з кольоровим тегом. Це вже зачіпає доменну модель (нове поле category в CalendarEvent + Room-міграція) і форму додавання.
**Складність: висока** — свідомо не рекомендується зараз, це major розширення бізнес-логіки, а не "непрямий" UI-приріст. Просто фіксую як ідею на майбутнє, якщо з'явиться сімейна фіча (кілька користувачів на одному календарі).

**Рекомендація:** A і B — дешеві покращення огляду. C відкласти — виходить за рамки "без ускладнення бізнес-логіки".

## 4. Список покупок (Shopping list)

Функціонально непогана: сортування, inline-редагування, ліміт. Прогалини:

### Варіант A — Групування "Ще купити" / "Куплено"
Зараз куплені товари просто перекреслюються і залишаються впереміш (порядок залежить від сортування). Розділити список на дві секції.
**Складність: низька-середня** (чиста UI-групування вже завантаженого списку по item.isBought — LazyColumn зі стікі-заголовками; без змін у domain/data).

### Варіант B — Підтвердження видалення (консистентність з Calendar)
Зараз видалення миттєве без діалогу — на відміну від Календаря, де є "Delete this event?". Або уніфікувати в бік підтвердження скрізь, або прибрати з Calendar — обрати один патерн для консистентності.
**Складність: низька.**

### Варіант C — "Очистити куплене" одною кнопкою
Замість видаляти куплені товари по одному через ✕.
**Складність: низька** (новий use case "delete all bought", простий bulk delete в Room DAO).

**Рекомендація:** A найбільш цінне (наочність довгого списку), C — приємний бонус, B — питання консистентності всього застосунку (див. розділ 6).

---

## 5. Список справ (Todo list)

Найпростіша фіча, ідентична Shopping без сортування. Прогалини аналогічні:

### Варіант A — Сортування (як у Shopping: Date / A–Z)
Зараз немає жодного сортування — порядок завжди "як створено". Перенести вже готовий ShoppingSortOrder-патерн.
**Складність: низька** (код-патерн уже є в Shopping, повторно застосувати).

### Варіант B — Приховати виконані / фільтр "Active only"
Toggle або чіп, що ховає задачі з isDone = true.
**Складність: низька** (чистий UI-фільтр над уже завантаженим списком).

### Варіант C — Групування виконано/невиконано (як Варіант A у Shopping)
**Складність: низька-середня**, аналогічно Shopping.

**Рекомендація:** B найпростіше і найкорисніше для типового todo-списку; A — для консистентності з Shopping, якщо це важливо власнику продукту.

## 6. Наскрізні (cross-feature) покращення

### Консистентність патернів видалення
Зараз Calendar використовує підтвердження, Shopping/Todo — ні. Варто свідомо обрати один підхід (наприклад: підтвердження лише там, де видалення "дорожче" відновити — календарна подія з датою/часом складніше відтворити, ніж рядок "Milk"). Якщо це усвідомлений вибір — фіксую в документі як "не потребує змін"; якщо ні — уніфікувати дешево (низька складність, лише UI).

### Порожні стани без заклику до дії
Усі три "порожні" екрани — це просто сірий текст. Можна додати короткий підказковий рядок ("Add your first item above") замість голого "list is empty" — суто текстова зміна.
**Складність: дуже низька.**

### Відсутність недавньої активності / feedback після дій
Додавання/редагування/видалення в Shopping і Todo не мають жодного візуального підтвердження (немає snackbar "Item added", на відміну від Calendar, де є snackbar на ліміт). Дрібне, але дешеве покращення — короткий Snackbar/Toast при видаленні (можливість Undo) замість тихого зникнення рядка.
**Складність: низька-середня** (якщо додавати Undo — потрібен тимчасовий стан "очікує на remove" в ViewModel, аналогічно pendingDeleteEvent у Calendar).

## Підсумок пріоритетів

1. **Home: картки зі зведенням (Варіант A)** — найбільший приріст цінності, головна сторінка справді "сира".
2. **Shopping: групування куплено/не куплено** — дешево, суттєво покращує довгі списки.
3. **Todo: фільтр "Active only"** — дешево, закриває явну прогалину порівняно з Shopping.
4. **Calendar: badge з кількістю подій у клітинці + кнопка "Today"** — дешеві покращення огляду вже сильної фічі.
5. **Консистентність видалення (з підтвердженням чи без) в усіх трьох списках** — питання свідомого рішення, не терміново.

Аутентифікація і форма додавання/редагування події в Календарі вважаю достатньо функціональними — суттєвих змін не пропоную, окрім дрібниці "показати пароль".
